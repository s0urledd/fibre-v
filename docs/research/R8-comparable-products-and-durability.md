## 1. Closest analogues in depth

### 1.1 Filecoin Spark (Checker Network) — closest analogue

**Status (important).** The checker repo `filecoin-station/spark` was archived on 2026-01-06 with the notice "This repository is no longer mantained" and "Filecoin Spark and Checker Network continue to operate in a permissioned architecture" ([github.com/filecoin-station/spark](https://github.com/filecoin-station/spark), seen 2026-09-08). `spark-evaluate` was archived 2026-01-07 ([github.com/filecoin-station/spark-evaluate](https://github.com/filecoin-station/spark-evaluate), seen 2026-09-08). The design below is the permissionless design as of the archived code; it is still the best-documented "measure serving from outside" system.

#### 1.1.1 Pipeline

| Stage | Component | What it does | Source |
|---|---|---|---|
| Round start | Meridian smart contract emits `RoundStart`; spark-api listens with `contract.on('RoundStart', onRoundStart)` | Rounds are ~20 minutes | [spark-api round-tracker.js](https://raw.githubusercontent.com/CheckerNetwork/spark-api/main/api/lib/round-tracker.js); [RSR SLI](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md) |
| Task list | `defineTasksForRound` samples eligible deals with `ORDER BY random() LIMIT $2` where the limit is `TASKS_PER_ROUND = 500`; rounds persisted in `spark_rounds` (`id, created_at, meridian_address, meridian_round, start_epoch, max_tasks_per_node`) | The list of what to check is fixed per round and served at `/rounds/current` | same |
| Node task selection | Checker computes `stationKey = SHA-256(stationId)`, `taskKey = SHA-256([cid, minerId, randomness].join('\n'))`, sorts tasks by `key ^ stationKey` (XOR distance), keeps the closest `maxTasksPerNode` (default 360); randomness is `getRandomnessForSparkRound(round.startEpoch)` from drand | Deterministic: anyone can recompute which node should have done which task | [spark tasker.js](https://raw.githubusercontent.com/filecoin-station/spark/main/lib/tasker.js) |
| Retrieval | HTTP and Bitswap via `ipfs://` URLs; "Abort if no progress was made for 60 seconds"; 10 s HEAD timeout; CAR blocks iterated with `CarBlockIterator`, hashes validated, root CID checked | Verifies content, not just a 200 | [spark spark.js](https://raw.githubusercontent.com/filecoin-station/spark/main/lib/spark.js) |
| Submission | `POST https://api.filspark.com/measurements` with 10 s timeout | Central API accepts raw measurements | same |
| Publication | Measurements are "batched to web3.storage/Storacha, committed on-chain" (`MeasurementsAdded` events on the Meridian contract) | Raw data is content-addressed and its CID is on-chain | [RSR SLI](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md); [spark-evaluate README](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/README.md) |
| Evaluation | spark-evaluate fetches each batch from `https://${cid}.ipfs.w3s.link?format=car` (14 retries), recomputes allowed tasks per node, groups into committees, derives result codes, writes public stats | "IMPORTANT: This algorithm must be in sync with the tasker in Spark checker nodes" | [preprocess.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/preprocess.js); [evaluate tasker.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/tasker.js) |
| Stats API | spark-stats serves `/retrieval-success-rate`, `/retrieval-result-codes/daily`, `/miner/:id/retrieval-success-rate/summary`, `/measurements/daily`, `/participants/daily` ... with `from`/`to` and `nonZero` | Public JSON | [spark-stats README](https://raw.githubusercontent.com/filecoin-station/spark-stats/main/README.md) |

Note on operational fragility they document: "Glif, the RPC API provider we use, keeps only ~16 hours of event history", so re-evaluating old rounds requires manually supplying CID lists ([spark-evaluate README](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/README.md)). And the checker's tasker has a TODO: "Without persistence, after the Spark module is restarted, it will start executing the same retrieval tasks we have already executed" ([tasker.js](https://raw.githubusercontent.com/filecoin-station/spark/main/lib/tasker.js)) — i.e. even Spark shipped without a resume cursor on the prober side.

#### 1.1.2 Measurement record (raw fields)

From [spark.js](https://raw.githubusercontent.com/filecoin-station/spark/main/lib/spark.js): `timeout, startAt, firstByteAt, endAt, carTooLarge, byteLength, carChecksum, statusCode, headStatusCode, providerId, indexerResult, protocol, providerAddress, sparkVersion, zinniaVersion, participantAddress, stationId`. The evaluator adds `inet_group`, `finished_at`, and derived `retrievalResult`, `taskingEvaluation`, `consensusEvaluation` ([preprocess.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/preprocess.js), [committee.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/committee.js)).

Two things to copy: (a) software versions (`sparkVersion`, `zinniaVersion`) are stored on every row, so the classifier/prober version is part of provenance; (b) timing is three timestamps (`startAt`, `firstByteAt`, `endAt`), not a single duration.

#### 1.1.3 How failure is represented: result codes, not booleans

`getRetrievalResult()` in [preprocess.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/preprocess.js) yields, in priority order: `IPNI_<indexer_result>` (unless indexer result is `OK` or `HTTP_NOT_ADVERTISED`), `TIMEOUT`, `CAR_TOO_LARGE`, `UNSUPPORTED_MULTIADDR_FORMAT` (status 700–799), then `UNKNOWN_FETCH_ERROR`, `HOSTNAME_DNS_ERROR`, `CONNECTION_REFUSED`, `CONTENT_VERIFICATION_FAILED`, `UNEXPECTED_CAR_BLOCK`, `CANNOT_PARSE_CAR_FILE` (600, 801–904), `HTTP_<status>` / `LASSIE_<status>` (≥300), `OK` (200–299 with `end_at` present), else `UNKNOWN_ERROR`.

Validity rules (`assertValidMeasurement`): valid participant address, non-null `inet_group`, positive `finished_at`, `indexerResult` present, and for `OK` results timestamps must satisfy `start_at ≤ first_byte_at ≤ end_at` and `head_status_code` must be consistent with the protocol.

#### 1.1.4 Scoring: RSR and what is in the denominator

- Formula in the SLI: "RSR = Successful Retrievals ÷ (Successful Retrievals + Contributing Failures)". Numerator: result `OK` after obtaining the SP's PeerID, querying IPNI, retrieving the root block and verifying it matches the CID. Denominator includes SP-attributable failures (connection refused, 60 s no-progress timeouts, content verification failures, 502/504, IPNI errors, unsupported multiaddr/hash) and excludes "RPC failures, outdated checker submissions, fraud-detection removals" ([RSR SLI](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md)).
- In code: `successRate = resultBreakdown.OK / totalForRSR` with `totalForRSR = totalCount - indexerServerErrorCount`, excluding `retrievalResult.match(/^IPNI_ERROR_5\d\d$/)` ([retrieval-stats.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/retrieval-stats.js)). The same exclusion appears in `buildPerPartyStats` ([public-stats.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/public-stats.js)). This is the "measurement-infrastructure fault is not the SP's fault" rule; our EXPECTED_GONE / TOLERATED classes are the analogous denominator carve-outs.
- The SLI caveats list is candid: "IPNI outages directly degrade SP RSR scores despite being outside provider control", "Self-generated checker IDs: Fraud mitigation relies on IPv4 /24 subnet limits rather than authentication", "Checker traffic distinguishable from legitimate traffic by payload CID patterns alone" ([RSR SLI](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md)).

#### 1.1.5 Anti-gaming (of checkers and of SPs)

| Threat | Mechanism | Source |
|---|---|---|
| Checker picks easy tasks / fabricates | Task set per node is a deterministic function of (task, drand randomness, stationId); evaluator recomputes allowed set with `getTasksAllowedForStations`; measurements outside it are rejected | [evaluate tasker.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/tasker.js) |
| Checker lies about result | Committees group measurements by `getTaskId(m)` = (cid, minerId); majority computed on `providerId, indexerResult, provider_address, protocol` then additionally `retrievalResult, byte_length, carChecksum`; labels `MAJORITY_RESULT`, `MINORITY_RESULT`, `MAJORITY_NOT_FOUND` (if `majoritySize <= this.size / 2`), `COMMITTEE_TOO_SMALL` | [committee.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/committee.js) |
| Sybil checkers on one network | `inet_group` (IPv4 /24) required on each measurement and used as dedupe key | [preprocess.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/preprocess.js); [RSR SLI](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md) |
| SP serves only checkers | Target 40–100 checkers per task (median ~80) from "real user networks"; the SLI admits checker traffic is distinguishable by CID pattern | [RSR SLI](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md) |

Caveats: in `evaluate.js` `REQUIRED_COMMITTEE_SIZE = 1` and every measurement gets `taskingEvaluation = 'OK'` in that file ([evaluate.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/evaluate.js)), and the SLI says FIL+ "uses non-committee (per-request) scoring: every individual measurement post-fraud-detection contributes to RSR". So committees exist for fraud flags but the headline number was per-measurement.

A note on "commit-reveal": none found in Spark. Spark's unpredictability comes from drand randomness fixed at `startEpoch`, and honesty from the evaluator recomputing assignments after the fact; there is no commit phase by checkers. Queries used: `"spark" filecoin checker "commit-reveal"`, `Space Meridian protocol docs "MeasurementsAdded" "RoundStart" evaluation service "committee"` (2026-09-08).

#### 1.1.6 Storage and publication of results

- Raw: append-only batches in IPFS CARs, CID on-chain. Evaluator caches "the list of MeasurementsAdded and the content of CIDs in the `.cache` directory" for dry-runs ([spark-evaluate README](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/README.md)).
- Derived: Postgres tables `retrieval_stats(day, miner_id, total, successful, successful_http, successful_http_head)`, `indexer_query_stats(day, deals_tested, deals_advertising_http)`, `daily_deals(day, miner_id, client_id, tested, index_majority_found, indexed, indexed_http, retrieval_majority_found, retrievable)`, `retrieval_timings(day, miner_id, ttfb_p50)`, `daily_client_retrieval_stats`, `daily_allocator_retrieval_stats`, `daily_miner_deals_checked(day, miner_id, payload_cids)`; all upserted with `ON CONFLICT(day, ...) DO UPDATE SET` by addition ([public-stats.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/public-stats.js)). Note that `total` and `successful` are stored side by side — the rate is always computed from stored counts.
- Public API: spark-stats endpoints above; base `http://stats.filspark.com/` ([README](https://raw.githubusercontent.com/filecoin-station/spark-stats/main/README.md)). Live fetch of `/retrieval-success-rate?from=2026-09-01&to=2026-09-07` failed (DNS timeout) on 2026-09-08, so response shape is taken from the table columns above, not a live sample.
- Dashboard: per search snippet, "records starting on April 7, 2024", a table of "Spark RSR and TTFB values calculated in aggregate for each Filecoin Storage Provider over the past 30 days", click-through per miner, plus a legacy Grafana dashboard ([dashboard.filspark.com via search](https://dashboard.filspark.com/), snippet seen 2026-09-08; direct fetch failed DNS). The original dashboard MVP issue lists as stretch goals "enriching the storage provider table with measurement counts and error categorization" ([roadmap issue #57](https://github.com/filecoin-station/roadmap/issues/57)).

#### 1.1.7 How missing / failed measurements are represented

- A failed probe is a row with a result code (never dropped). Per-round `resultBreakdown` initialises only `OK` and `TIMEOUT`; other keys appear only when present: "We are intentionally not initializing all possible keys here" ([retrieval-stats.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/retrieval-stats.js)).
- Infrastructure faults (IPNI 5xx) are excluded from the denominator rather than counted as success or failure.
- Missing timestamps simply prevent TTFB/duration computation for that row; invalid byte lengths become `undefined` and are excluded from size stats ([retrieval-stats.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/retrieval-stats.js)).
- What is **not** found: any explicit "evaluator was down / round not evaluated" marker in the public tables. Queries: `spark-evaluate "round not evaluated" missing round`, `spark-stats gap days missing rounds` (2026-09-08). The `/measurements/daily` and `/participants/daily` endpoints are the only visible way to see a day with unusually few measurements.

**Storj satellite audits** ([online score FAQ](https://storj.dev/node/faq/how-the-online-score-is-calculated), [disqualification FAQ](https://storj.dev/node/faq/why-is-my-node-disqualified), [reputation package docs](https://pkg.go.dev/storj.io/storj/satellite/reputation), [audit-suspend blueprint](https://raw.githubusercontent.com/storj/storj/6c34ff64adde51c5d819b2800ef1e59f67f75f0e/docs/blueprints/audit-suspend.md), [downtime-tracking blueprint](https://raw.githubusercontent.com/storj/storj/c2a97aeb143791dd7edd8bea5bb43558a95b57de/docs/blueprints/storage-node-downtime-tracking-with-audits.md), all seen 2026-09-08)

| Aspect | Storj |
|---|---|
| What | Satellites audit random erasure shares. Five outcomes: "Success: The node responds with the correct data", "Failure: The node responds with incorrect data", Offline, Contained (connection timeout), Unknown (any other error). "Only cases 1 and 2 directly affect a node's audit reputation". |
| Scores | Audit reputation is an alpha/beta model: `InitialAlpha` 1000, `InitialBeta` 0, `AuditLambda` 0.999 ("the forgetting factor"), `AuditDQ` 0.96 (disqualify below 96%), `UnknownAuditDQ` 0.6, `SuspensionGracePeriod` 168h, `AuditCount` 100 before a node stops being "New", `MinimumNodeAge` 504h. |
| Online score (downtime) | "12-hour windows and a 30-day tracking period, which translates to 60 windows per tracking period"; per-window score = online audits / total audits (e.g. 1 offline of 10 → 0.9); overall = mean of windows; example "(59 * 1.0 + 1 * 0.9)/60 = 0.99833"; reported to the node "with some delay (up to 12 hours)". Suspension below 60%; then "a week to fix the issue"; then "the node needs to stay online for the next 30 days to recover fully". |
| Why audits, not pings | The downtime blueprint moved from a ping ratio because reputation could "quickly become destroyed over a relatively short period of downtime" for nodes with many pieces; windows "minimize the effect of any particularly unlucky period". |
| Why "unknown" is separate | "Case 5 is the only situation where there is currently no potential penalty for responding to an audit with some type of error"; and "we want to avoid disqualifying storagenodes for simple configuration mistakes that cause them to return errors during audits, but we also want to avoid making these types of errors consequence-free" — hence a suspension mode that stops new ingress "until it passes enough audits". |
| Anti-gaming | Random piece selection by the satellite; the node cannot predict which piece is audited; containment re-audits timeouts rather than trusting them. |
| UI | Node dashboard shows audit/online/suspension scores per satellite (colour threshold updated for the 96% rule, [storj/storj#5113](https://github.com/storj/storj/issues/5113)). |

## 2. Data-loss prevention for a chain-following collector plus a prober

### 2.1 Finality and cursors

- CometBFT commits a block on "+2/3 precommits for a particular block"; the safety argument is that once a validator commits at round R, "1/3+ of honest nodes are still locked at round R' > R", so "the chain never forks" with <1/3 Byzantine power ([CometBFT consensus spec](https://raw.githubusercontent.com/cometbft/cometbft/main/spec/consensus/consensus.md), seen 2026-09-08). Cosmos docs state it plainly: "Once a block is committed, it cannot be reverted." ([Cosmos SDK app architecture](https://docs.cosmos.network/sdk/latest/learn/intro/sdk-app-architecture)).
- Consequence: the collector needs one monotonic cursor (`last_indexed_height`) and no reorg buffer. Celenium still keeps a rollback path keyed on hash mismatch (1.4) — cheap insurance against a misbehaving RPC peer; we can do the cheaper thing: store `block_hash` per height and refuse to advance if the parent hash of height h+1 does not match our stored hash at h.
- Idempotency keys that follow from finality: `(height, tx_index, msg_index)` for MsgPayForFibre publications; `(height, validator_address)` for endpoint-registration events; `(height)` for params snapshots. Spark's equivalent is `ON CONFLICT(day, miner_id, ...) DO UPDATE` on derived tables (1.1.6) and content-addressed CIDs for raw batches.
- Event subscriptions are not a durable source. CometBFT's `experimental_subscription_buffer_size` is "the maximum number of events a node will buffer, per subscription, before returning an error and closing the subscription", and `experimental_close_on_slow_client` will "cause the WebSocket connection to be closed instead if it cannot read fast enough" ([config/toml.go](https://raw.githubusercontent.com/cometbft/cometbft/main/config/toml.go), seen 2026-09-08). Use WebSocket only as a wake-up; always advance by polling `/block` and `/block_results` from the cursor.

### 2.2 Backfill after downtime and what to do when pruning has passed the gap

- On restart, read `last_indexed_height`, call `/status` and compare with `sync_info.earliest_block_height` / `latest_block_height` (fields `"earliest_block_height"`, `"latest_block_height"`, `"catching_up"` in `SyncInfo`, [rpc/core/types/responses.go](https://raw.githubusercontent.com/cometbft/cometbft/main/rpc/core/types/responses.go), seen 2026-09-08).
- If `last_indexed_height + 1 < earliest_block_height`, the node has pruned the gap. The RPC will answer `"height %d is not available, lowest height is %d"` ([rpc/core/env.go](https://raw.githubusercontent.com/cometbft/cometbft/main/rpc/core/env.go), seen 2026-09-08). Pruning is controlled on the app side by `min-retain-blocks`: "Minimum block height offset from the current block being committed, such that blocks past this offset may be pruned from CometBFT"; default `0` = no pruning ([cosmos-sdk server/config/config.go](https://raw.githubusercontent.com/cosmos/cosmos-sdk/main/server/config/config.go), seen 2026-09-08).
- Policy: (1) try a second RPC (archive or longer-retention node) for the gap; (2) if none, write a `collector_gaps(from_height, to_height, reason='rpc_pruned', discovered_at, rpc_url)` row and continue from `earliest_block_height`; render the gap on the dashboard (never as zero publications). Spark hit the same class of problem with its RPC provider keeping "only ~16 hours of event history" (1.1.1).
- Prober side: the prober's "cursor" is the set of (blob, validator) assignments still inside the 4-hour retention window. On restart, re-derive the schedule from stored publications and record `probe_runs` with `resumed_from`; Spark's tasker explicitly lacks this and re-executes tasks after restart (1.1.1).

### 2.3 Append-only raw records vs derived tables; rebuilding

| Layer | Content | Mutability | Analogue |
|---|---|---|---|
| Raw JSONL from probe tools | One record per probe attempt with all fields (timestamps, bytes, error class, endpoint, prober version, commitment, rows verified) | Append-only, one file per (tool, day or hour), gzip after close | Spark raw measurement batches on IPFS (1.1.6); Xatu Parquet per day (1.2) |
| Ingest cursor | `(file_path, byte_offset)` per file, advanced only after the SQLite tx commits | Idempotent: primary key on `probe_id` (derive as hash of `(tool, prober_id, blob_id, validator, started_at)`) so re-reading a file is a no-op | Blobscan `--slots-per-save` checkpointing; Celenium state table |
| Derived tables | Per-day/per-validator counts (`total`, by class), percentiles | Recomputed; must be reproducible by a one-shot job from raw | Spark `retrieval_stats(day, miner_id, total, successful, ...)` upserts |
| Classifier version | `classifier_version` column on every derived row; raw rows never store a class, only facts | Re-classification = re-run derivation with new version, keep old rows for comparison | Spark stores `sparkVersion`/`zinniaVersion` per measurement; `retrievalResult` is derived in the evaluator, not the checker (1.1.2–1.1.3) |

Rule of thumb from Spark: the checker records *facts* (`statusCode`, `timeout`, `carTooLarge`, `carChecksum`, timestamps); the *label* (`retrievalResult`, `consensusEvaluation`) is computed centrally and can be recomputed. Keep that split.

### 2.4 SQLite durability

| Setting / tool | What the docs say | Recommendation for MVP |
|---|---|---|
| `PRAGMA journal_mode=WAL` | "Readers do not block writers and a writer does not block readers"; "WAL does not work over a network filesystem"; "For transactions larger than about 100 megabytes, traditional rollback journal modes will likely be faster"; auto-checkpoint at 1000 pages ([sqlite.org/wal.html](https://sqlite.org/wal.html), seen 2026-09-08) | Use WAL on local disk only; keep ingest transactions small (per file chunk) |
| `PRAGMA synchronous` | NORMAL: "The SQLite database engine will still sync at the most critical moments, but less often than in FULL mode. There is a very small (though non-zero) chance that a power failure at just the wrong time could corrupt the database." Recommendation: "The synchronous=NORMAL setting provides the best balance between performance and safety for most applications running in WAL mode. You lose durability across power loss with synchronous NORMAL in WAL mode, but that is not important for most applications." ([pragma.html#pragma_synchronous](https://sqlite.org/pragma.html#pragma_synchronous)); wal.html adds that in NORMAL "transactions are no longer durable and might rollback following a power failure" | NORMAL is acceptable because the raw JSONL is the source of truth and can be re-ingested; use FULL if the SQLite file is the only copy of anything |
| `PRAGMA busy_timeout` | "It is recommended to set this to 5 seconds: PRAGMA busy_timeout = 5000;" ([litestream tips](https://litestream.io/tips/)) | Set on every connection |
| `PRAGMA wal_autocheckpoint=0` | Litestream: "This prevents the application from checkpointing between Litestream's operations, which could cause missed updates and unnecessary full snapshots" ([tips](https://litestream.io/tips/)) | Set when Litestream is attached |
| Litestream | "Litestream only works with the SQLite WAL journaling mode"; it "effectively [takes] over the checkpointing process" and "starts a long-running read transaction to prevent any other process from checkpointing"; packages pages into LTX files with monotonically increasing TXIDs; snapshots "every 24 hours" by default; restore fetches "the most recent snapshot that does not overshoot the requested restore point and then applies each subsequent LTX file in TXID order" ([how it works](https://litestream.io/how-it-works/)). Defaults: `sync-interval` 1s, `snapshot.interval` 24h, `snapshot.retention` 24h, `checkpoint-interval` 1m, `min-checkpoint-page-count` 1000; replica types include `s3` (also "Backblaze B2, DigitalOcean Spaces, MinIO, and Tigris"), `gs`, `abs`, `sftp`, `file`, `nats`, `oss`, `webdav`; S3-compatible endpoints need `endpoint` and `force-path-style` is "automatically enabled if endpoint is set" ([config reference](https://litestream.io/reference/config/)). Warning: "Multiple applications replicating into the same bucket & path can cause situations where you will be unable to restore." ([tips](https://litestream.io/tips/)) | Replicate to an S3-compatible bucket (R2 works via `endpoint`); one Litestream per DB file; data-loss window ≈ `sync-interval` |
| Restore | `litestream restore -o PATH`, `-timestamp` / `-txid` for point-in-time, `-if-replica-exists`, `-if-db-not-exists`, `-dry-run`, `-integrity-check quick|full`; "not every transaction ID represents a valid restoration endpoint" ([restore reference](https://litestream.io/reference/restore/)) | Drill: restore to a temp path with `-integrity-check full`, then run the derived-table rebuild and compare counts |
| Backup API / `VACUUM INTO` | Backup API copies pages incrementally and "usually restarts the backup process" if another connection writes; `VACUUM INTO` "is transactional in the sense that the generated output database is a consistent snapshot of the original database", output is fsync'd only "if the PRAGMA synchronous setting of the original database is NORMAL or FULL" ([backup.html](https://sqlite.org/backup.html), [lang_vacuum.html](https://sqlite.org/lang_vacuum.html)) | Nightly `VACUUM INTO` to a dated file as a second, Litestream-independent backup |
| Do not `cp` a live DB | "Systems that run automatic backups in the background might try to make a backup copy of an SQLite database file while it is in the middle of a transaction" → copy "might contain some old and some new content, and thus be corrupt"; never delete `-wal`/`-shm` after a crash: "automatic recovery will not work and the database may go corrupt" ([howtocorrupt.html](https://sqlite.org/howtocorrupt.html)) | Backups only via Litestream / `VACUUM INTO` / backup API |
| When to move to Postgres | "SQLite supports an unlimited number of simultaneous readers, but it will only allow one writer at any instant in time"; "If there are many client programs sending SQL to the same database over a network, then use a client/server database engine"; size limit "281 terabytes"; "For device-local storage with low writer concurrency and less than a terabyte of content, SQLite is almost always a better solution." ([whentouse.html](https://sqlite.org/whentouse.html)) | Move when: (a) API and ingest must run on different hosts, (b) more than one writer process (e.g. several probers writing directly), or (c) you need concurrent heavy analytical queries during ingest |

### 2.5 Postgres equivalents (brief)

- Continuous archiving: set `wal_level=replica`, `archive_mode=on`, `archive_command` (must "return zero exit status if and only if it succeeds"); base backup with `pg_basebackup -D ... -X stream`; PITR by `restore_command` + `recovery.signal`; "It is possible to restore the database to its state at any time since your base backup was taken." ([PostgreSQL continuous-archiving](https://www.postgresql.org/docs/current/continuous-archiving.html), seen 2026-09-08).
- pgBackRest: "Full, differential, and incremental backups are supported", "S3, Azure, and GCS compatible object stores", "Checksums are calculated for every file in the backup and rechecked during a restore or verify", "an interrupted backup can be resumed", "Parallel, asynchronous WAL push & get", retention policies ([pgbackrest.org](https://pgbackrest.org/), seen 2026-09-08).
- Celenium uses Postgres/TimescaleDB with hypertables and a single transaction per block (1.4) — the natural target schema when we migrate.

### 2.6 Recording observer downtime explicitly

None of the surveyed products publishes an "observer was down" table; the closest are tenderduty's instantaneous `alert_if_no_servers`, L2BEAT's "Running since <timestamp>" status page, Celenium's `synced`/`last_time` in `/head`, and Storj's windowed online score where a window with zero audits simply does not contribute (1.3, 1.4, 1.5). Grafana's standard rendering rule is that nulls are gaps unless explicitly connected: "Never — Time series data points with gaps in the data are never connected"; "Threshold — Specify a threshold above which gaps in the data are no longer connected" ([Grafana time series docs](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/visualizations/time-series/), seen 2026-09-08).

Concrete schema (ours, motivated by the above):

| Table | Columns | Purpose |
|---|---|---|
| `observer_runs` | `run_id, component ('collector'|'prober'|'ingest'|'api'), version, started_at, last_heartbeat_at, ended_at, end_reason, host, vantage_id` | One row per process lifetime; heartbeat every N seconds |
| `collector_gaps` | `from_height, to_height, reason ('down'|'rpc_pruned'|'rpc_unreachable'), discovered_at, filled_at` | Derived from `observer_runs` gaps plus RPC errors; `filled_at` set when backfilled |
| `probe_gaps` | `vantage_id, from_ts, to_ts, reason` | Derived from prober heartbeats; dashboards render as hatched regions, not zero |
| `probe_rows` (derived counts) | `bucket_start, validator, class, count, classifier_version` | Never store a bucket row for a bucket fully inside a gap; API returns `null` with `gap_reason` |

### 2.7 Measurement provenance and classifier versioning

- Per raw row: `prober_version`, `vantage_id`, `rpc_url` used for the publication, `started_at/first_byte_at/ended_at` (Spark's three timestamps), `clock_drift` (Xatu records NTP drift per client, 1.2), request/response sizes, and the verification facts (rows checked, commitment matched, which shard).
- Per derived row: `classifier_version` and `derived_at`. Keep the previous version's rows until a re-derivation has been compared; expose `?classifier_version=` on the API.
- Committee-style cross-checking is not available with one vantage; the substitute is publishing the raw rows and the deterministic classifier so anyone can re-derive (Spark's "must be in sync" evaluator, 1.1.1).

### 2.8 Backups, restore drills, and retention sizing

Arithmetic (ours, from the brief's numbers): 300k rows/day × ~2 KB ≈ 600 MB/day raw at stress; 30 days ≈ 18 GB; 90 days ≈ 54 GB uncompressed. Far below SQLite's 281 TB limit ([whentouse.html](https://sqlite.org/whentouse.html)) but large for Litestream snapshots every 24 h and for `VACUUM INTO`.

| Tier | Keep | Where | Notes |
|---|---|---|---|
| Raw JSONL (gzipped after file close) | Indefinitely, or ≥ 13 months | Object storage (S3/R2), immutable object names `tool/YYYY/MM/DD/HH.jsonl.gz` | Mirrors Xatu's per-day Parquet paths (1.2); this is the reprocessing source |
| SQLite raw-ingested rows | 30–90 days | Local disk + Litestream | Delete by `started_at < cutoff` in small batches; then `VACUUM INTO` nightly |
| Derived daily/hourly counts | Indefinitely | SQLite (small) | Rebuildable from raw |
| Litestream replica | `snapshot.retention` raised from default 24h to ≥ 7d | S3/R2 | Data-loss window ≈ 1 s `sync-interval` |
| Restore drill | Weekly automated: `litestream restore -o /tmp/x.db -integrity-check full`, rebuild derived tables from a sample of raw files, compare `count(*)` per day with production | CI job | Litestream advises `-dry-run` first because "not every transaction ID represents a valid restoration endpoint" ([restore reference](https://litestream.io/reference/restore/)) |

## 4. Recommendations (numbered design decisions)

1. **MVP durability stack = SQLite in WAL mode, `synchronous=NORMAL`, `busy_timeout=5000`, `wal_autocheckpoint=0`, one Litestream process per DB file replicating to an S3-compatible bucket (R2 via `endpoint`), plus nightly `VACUUM INTO` to a dated file.** Sources: [sqlite.org/wal.html](https://sqlite.org/wal.html), [pragma synchronous](https://sqlite.org/pragma.html#pragma_synchronous), [litestream tips](https://litestream.io/tips/), [litestream config](https://litestream.io/reference/config/), [lang_vacuum.html](https://sqlite.org/lang_vacuum.html). Raise `snapshot.retention` above the 24 h default. Never back up by `cp` ([howtocorrupt.html](https://sqlite.org/howtocorrupt.html)).
2. **Treat gzipped raw JSONL in object storage as the system of record; SQLite is a rebuildable index.** This is what makes `synchronous=NORMAL` safe and what Spark (raw batches on IPFS, evaluator recomputes) and Xatu (Parquet per day) do. Sources: [RSR SLI](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md), [xatu-data README](https://raw.githubusercontent.com/ethpandaops/xatu-data/master/README.md).
3. **Move to Postgres only when a second writer process or a second host needs the DB, or analytical load interferes with ingest**; migrate to the Celenium-style single-transaction-per-block schema with TimescaleDB hypertables, and adopt WAL archiving + pgBackRest at that point. Sources: [whentouse.html](https://sqlite.org/whentouse.html), [Celenium README](https://raw.githubusercontent.com/celenium-io/celestia-indexer/master/README.md), [PostgreSQL PITR](https://www.postgresql.org/docs/current/continuous-archiving.html), [pgbackrest.org](https://pgbackrest.org/).
4. **Collector: single monotonic height cursor, no reorg buffer, parent-hash check as a cheap guard, WebSocket only as a wake-up, poll `/block` + `/block_results` from the cursor.** Sources: [CometBFT consensus spec](https://raw.githubusercontent.com/cometbft/cometbft/main/spec/consensus/consensus.md), [Cosmos SDK architecture](https://docs.cosmos.network/sdk/latest/learn/intro/sdk-app-architecture), [config/toml.go subscription buffer warnings](https://raw.githubusercontent.com/cometbft/cometbft/main/config/toml.go), [Celenium receiver.go](https://raw.githubusercontent.com/celenium-io/celestia-indexer/master/pkg/indexer/receiver/receiver.go).
5. **On restart, compare the cursor with `/status.sync_info.earliest_block_height`; if pruned past the gap, try a second RPC, else write a `collector_gaps` row with `reason='rpc_pruned'` and continue.** Sources: [SyncInfo fields](https://raw.githubusercontent.com/cometbft/cometbft/main/rpc/core/types/responses.go), [env.go error string](https://raw.githubusercontent.com/cometbft/cometbft/main/rpc/core/env.go), [min-retain-blocks](https://raw.githubusercontent.com/cosmos/cosmos-sdk/main/server/config/config.go), Spark's "~16 hours of event history" problem ([spark-evaluate README](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/README.md)).
6. **Idempotent ingest: primary key `probe_id = hash(tool, vantage_id, blob_id, validator, started_at)`; ingest cursor `(file, byte_offset)` committed in the same SQLite transaction as the rows.** Analogues: Spark `ON CONFLICT ... DO UPDATE` upserts ([public-stats.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/public-stats.js)), Blobscan `--slots-per-save` checkpoints ([indexer docs](https://docs.blobscan.com/docs/indexer)).
7. **Store facts in raw rows, labels in derived rows, with `classifier_version` on every derived row; re-classification is a rerun, never an in-place update.** Source: Spark's split between checker fields and evaluator-derived `retrievalResult`/`consensusEvaluation` ([preprocess.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/preprocess.js), [committee.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/committee.js)); Xatu's per-event client version and `clock_drift` ([event_ingester.proto](https://raw.githubusercontent.com/ethpandaops/xatu/master/pkg/proto/xatu/event_ingester.proto)).
8. **Record observer liveness in `observer_runs` (heartbeats) and materialise `collector_gaps` / `probe_gaps`; the API returns `null` + `gap_reason` for buckets inside a gap; charts use "never connect nulls".** Sources: tenderduty `alert_if_no_servers` / `node_down_alert_minutes` ([example-config.yml](https://raw.githubusercontent.com/blockpane/tenderduty/main/example-config.yml)), L2BEAT "Running since" status page ([um-prod.l2beat.com](https://um-prod.l2beat.com/status/discovery)), Celenium `/head` `synced`/`last_time` ([live](https://api-mainnet.celenium.io/v1/head)), Grafana null handling ([docs](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/visualizations/time-series/)).
9. **Failure is a code, not a boolean: keep an ordered result-code derivation like Spark's (`TIMEOUT`, `CONNECTION_REFUSED`, `HOSTNAME_DNS_ERROR`, `CONTENT_VERIFICATION_FAILED`, `HTTP_<n>`, `UNKNOWN_ERROR`) beneath our HEALTHY/FAULT/TOLERATED/EXPECTED_GONE classes, and serve a daily code histogram per validator.** Sources: [preprocess.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/preprocess.js), [spark-stats `/retrieval-result-codes/daily`](https://raw.githubusercontent.com/filecoin-station/spark-stats/main/README.md).
10. **Denominator carve-outs must be explicit and documented: observer-side faults (our DNS, our RPC, our timeouts under load) are excluded from the validator's rate the way Spark excludes `IPNI_ERROR_5xx`; publish the carve-out table on the methodology page.** Sources: [retrieval-stats.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/retrieval-stats.js), [RSR SLI](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md).
11. **Keep an explicit UNKNOWN class separate from FAULT** (probe could not conclude: e.g. commitment not yet indexed, partial download aborted by us), following Storj's "Unknown" audit outcome and ProbeLab's "Unknown" agent bucket. Sources: [audit-suspend blueprint](https://raw.githubusercontent.com/storj/storj/6c34ff64adde51c5d819b2800ef1e59f67f75f0e/docs/blueprints/audit-suspend.md), [probelab.io/celestia](https://probelab.io/celestia/).
12. **Windowed scoring with stated lag: compute validator serving scores over fixed windows (e.g. 1 h buckets over the 4 h retention, then daily over 30 d) and state the reporting delay, as Storj does (12 h windows × 60, "up to 12 hours" delay).** Source: [online score FAQ](https://storj.dev/node/faq/how-the-online-score-is-calculated). Windows also make gaps visible as missing windows rather than depressed averages.
13. **Un-gameability with one vantage: make sampling deterministic and post-hoc verifiable rather than secret.** Pick which shard/row-range to probe for each (blob, validator, slot) as `SHA-256(commitment ‖ validator ‖ round_randomness)` where `round_randomness` is something the validator cannot precompute far ahead and we cannot choose — Spark uses drand at `startEpoch`; on Celestia the block hash of the height at which the probe round opens is a natural analogue (this is our proposal, not sourced). Publish the algorithm and the raw rows so anyone can recompute the assignment, as Spark's evaluator does ("IMPORTANT: This algorithm must be in sync with the tasker"). Spark does **not** use commit-reveal (none found, 1.1.5); a commit-reveal step is only needed if multiple independent probers must not copy each other's results. Sources: [spark tasker.js](https://raw.githubusercontent.com/filecoin-station/spark/main/lib/tasker.js), [evaluate tasker.js](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/lib/tasker.js).
14. **Reduce "serve only the observer" gaming the way the RSR SLI admits it cannot fully: rotate egress IPs/vantages when possible, randomise probe timing within the window (Spark adds `jitter = Math.round(Math.random() * maxJitterInMs)`), and show on the validator page that the observer is a single, identifiable client.** Sources: [spark.js](https://raw.githubusercontent.com/filecoin-station/spark/main/lib/spark.js), [RSR SLI caveats](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md).
15. **Stake-weighted context, not stake-weighted verdicts: show each validator's voting-power share next to its serving rate (EigenDA ties SLA strictness to stake share) but keep the class thresholds identical for all.** Source: [protocol-SLA.md](https://raw.githubusercontent.com/Layr-Labs/eigenda-docs/master/docs/operator-guides/requirements/protocol-SLA.md).
16. **Expose raw data three ways: (a) `/v1/probes?validator=&from=&to=` paginated JSON with every stored field; (b) daily gzipped JSONL/Parquet at stable URLs `raw/<tool>/YYYY/MM/DD.jsonl.gz` under an open licence (Xatu uses CC BY 4.0); (c) an open-source `reclassify` CLI that takes those files and reproduces the derived tables (Spark's `bin/dry-run.js` with CSV export).** Sources: [xatu-data README](https://raw.githubusercontent.com/ethpandaops/xatu-data/master/README.md), [spark-evaluate README](https://raw.githubusercontent.com/filecoin-station/spark-evaluate/main/README.md).
17. **API conventions: version prefix `/v1/`, `from`/`to` date params, `Cache-Control` on aggregates, 429 on rate limit, optional API key header for higher tiers.** Sources: [spark-stats README](https://raw.githubusercontent.com/filecoin-station/spark-stats/main/README.md), [api-docs.celenium.io](https://api-docs.celenium.io/).
18. **UI conventions to borrow:** L2BEAT-style colour cells that link to the definition of the class ([DA risk page](https://l2beat.com/data-availability/risk)); ProbeLab-style denominators in the header of every chart ("N probes, M validators, window X–Y UTC") and method-change annotations on the timeline ([2024-47 report](https://probelab.io/celestia/dht/2024-47/)); a public `/status` page with "running since", last ingested height, last probe time and current gaps ([um-prod.l2beat.com](https://um-prod.l2beat.com/status/discovery), [celenium /head](https://api-mainnet.celenium.io/v1/head)); Spark-style per-entity summary tables (RSR and TTFB over 30 d with click-through) with measurement counts in the row ([dashboard.filspark.com](https://dashboard.filspark.com/) via search snippet; [roadmap #57](https://github.com/filecoin-station/roadmap/issues/57)).
19. **Methodology page contents (modelled on the RSR SLI document): definition of each class with the exact code paths; the denominator table (counted / not counted); sampling algorithm; vantage description; known limitations written as bluntly as Spark's ("Checker traffic distinguishable from legitimate traffic"); a changelog of classifier versions with dates.** Source: [RSR SLI](https://github.com/filecoin-project/service-classes/blob/main/service-level-indicators/spark-retrieval-success-rate.md), [L2BEAT FAQ disclaimers](https://l2beat.com/faq).
20. **Retention: raw JSONL in object storage ≥ 13 months; SQLite raw rows 30–90 days then deleted in batches followed by `VACUUM INTO`; derived counts forever; weekly automated restore drill with `-integrity-check full` and a derived-table diff.** Sources: [litestream restore](https://litestream.io/reference/restore/), [lang_vacuum.html](https://sqlite.org/lang_vacuum.html); sizing arithmetic in 2.8 is ours.
